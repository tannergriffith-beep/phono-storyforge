# Phono StoryForge

### A closed-loop reading tutor that writes a book proven decodable for one specific child, then gets smarter every time that child reads out loud

**Track: Agents for Good (education)**

## The problem

If your child struggles to read, the standard advice is simple: give them decodable books at their exact level. In practice that advice is almost impossible to follow, for two reasons.

First, a decodable book at the precise intersection of a child's phonics level, age, and interests barely exists. Publishers can't print enough permutations to cover every kid.

Second, and worse, nothing is watching what the child actually gets wrong. A worksheet doesn't know that Sam keeps missing "wh" but has "ck" down cold. So the next book he gets is whatever's next in the binder, not what he actually needs to practice. There's no loop.

Phono StoryForge closes that loop. It generates a book guaranteed to be decodable for this child, watches them read it aloud, figures out exactly which sound tripped them up, and lets that shape the next book. Adaptive rather than static, and it can prove the adaptive version is worth building.

This is my submission to Google and Kaggle's 5-Day AI Agents Intensive, Vibe Coding Capstone, in the Agents for Good track.

## Why an agent, not a script

You could write a static decodable-book generator with string templates and a word list. People have. What you can't easily do with a script is the part that makes this useful: propose a story an LLM is good at (character, plot, a kid's interests), verify it against a hard constraint a script is good at (is every word actually decodable at this level), and loop between the two until both are satisfied. That negotiation between a creative proposer and a deterministic verifier is the actual job here, and it's where agents earn their keep over a plain generation pipeline.

## Architecture

The spine is one loop that runs per child, per session:

`LearnerProfile → select_objective() → generate a decodable book → child reads aloud → assess() (miscue and grapheme attribution) → update_from_evidence() (Bayesian Knowledge Tracing) → back to LearnerProfile`, with the next session's target shifting based on what just happened.

The claim I want to make plainly: everything load-bearing in that loop is deterministic, non-LLM Python, and it's unit tested. The LLM proposes. Deterministic code decides.

Five modules do the real work:

| Step | Module | Role |
|---|---|---|
| Plan | `planner.py`, `select_objective` | Picks the lowest unmastered grapheme (zone of proximal development) from the BKT estimate, plus spaced review |
| Decode | `decodability.py`, `decompose` | The keystone: breaks a word into ordered graphemes tagged by phonics level. Single source of truth for decodability, targeting, and miscue attribution |
| Assess | `alignment.py`, `assess` | Aligns what was expected against what was spoken (running-record miscue types), attributes each error to the exact grapheme responsible |
| Update | `mastery.py`, `update_from_evidence` | Four-parameter Bayesian Knowledge Tracing updates per-grapheme knowledge state |
| Persist | `app/store/` | `LearnerProfile` (current mastery) plus an append-only session history |

The part I'd want a judge to notice: the same code that runs the live product loop is the code the evidence experiment below exercises. The simulation isn't a detached toy built to look good in a chart. It's a calibration harness running against the production brain.

The illustrated book pipeline used to be a separate path. As of commit `e7d815b`, it's folded into the live loop: the web UI triggers generation directly, reusing the same story planner and QA-loop agents rather than a parallel copy. One export distinction worth being precise about: the live web flow assembles the exported document deterministically. There's a second, LLM-drives-MCP export path that stays wired up for `adk web` and integration testing, but I'm not claiming it's reliable standalone, so it doesn't ship in the live flow.

The propose-then-verify pattern above shows up three times in this codebase, not once:

The decodability QA loop is a `LoopAgent` wrapping a custom `BaseAgent` that re-runs the writer until a deterministic check confirms zero decodability violations, or halts. This is a hard gate. An undecodable word raises an error rather than quietly passing through with a flagged violation.

The palette verifier checks every illustrated page generated by Gemini's image model against the brand palette using nearest-color distance, with a tolerance and a drift budget. Off-palette pages get regenerated or snapped back, automatically.

Document export separates concerns the same way: the LLM writes the text, and separate deterministic code assembles the actual document, choosing a dyslexia-friendly body typeface and embedding the images.

All three are guardrails that halt on failure instead of silently continuing, which is the property I actually care about here. A tutor that occasionally hands a struggling reader an undecodable word isn't a minor bug, it undermines the entire premise of the product.

For judges checking off the capstone's technical concepts, this project uses a multi-agent `SequentialAgent` with a `LoopAgent`-wrapped QA guardrail, agent skills (the deterministic modules above), closed-loop memory via `LearnerProfile`, Gemini Live for the voice interaction, a live FastAPI/WebSocket web app, MCP over stdio for Drive, Docs, and Gmail, and OpenTelemetry tracing. There's also a Dockerfile and a Cloud Run deployment path defined in the repo. I have not deployed it live, and I'd rather say that plainly than let a judge discover it.

## The evidence: does adaptive actually beat static?

I didn't want to just assert that adapting to a child's real mistakes works better than a fixed curriculum. I built an experiment to check.

`adaptive_vs_static.py` runs two arms over the same paired, seeded simulated learners. One arm picks each session's target from the child's live BKT estimate. The other follows a fixed scope-and-sequence and ignores the evidence entirely. Both arms close the identical loop, and both get tested against the same fixed benchmark probe each session, so the fluency comparison is fair. The whole thing is deterministic and LLM-free, so it reproduces exactly, every run.

Here are the headline numbers, from a de-circularized rerun (n=30 simulated learners, 40 sessions each):

| Metric | Earlier, circular version | De-circularized headline |
|---|---|---|
| Probe accuracy gap | +0.14 | +0.06 (exactly +0.0605) |
| True mean latent mastery gap | +0.09 | +0.04 |
| Words-correct-per-minute gap | +16 | +4.9 (derived, see caveat below) |
| Graphemes mastered (≥0.95) gap | positive | −0.47, a wash |

I want to be upfront about what "de-circularized" means and why the numbers dropped. The first version of this experiment had a subtle problem: the simulated learner's behavior was close enough to how BKT itself models learning that adaptive was partly winning by construction, not by genuinely tracking a real gap. So I rebuilt the simulated learner with two deliberate mismatches against the planner's own model. It emits correct/incorrect answers through a four-parameter logistic item-response curve with per-grapheme item difficulty, which is non-linear and item-specific in a way plain BKT's level-uniform slip and guess parameters can't represent. And I deleted the prerequisite gate the planner assumes exists, replacing it with active forgetting: mastery decays for any grapheme the child hasn't practiced recently. The planner's whole thesis, that prerequisites unlock later learning, isn't even true of the simulated learner anymore. So if adaptive still wins, it's winning by actually tracking a moving target, not by matching its own assumptions back to itself.

It still wins, but the win got smaller once I removed that structural advantage. Roughly half the size, across every metric. I think that's the honest result, and I'd rather report a real halved gap than an inflated one that doesn't survive scrutiny.

Two of those four metrics are genuinely independent evidence: the accuracy gap and the mean latent mastery gap. The words-correct-per-minute number is derived (a deterministic function of the error count), so it tracks the accuracy result rather than adding a third independent line of evidence, and I don't think it's honest to sell it as one. The mastery-count metric (crossing a hard 0.95 threshold) is close to a wash, slightly negative for adaptive, because a fixed drill schedule over-concentrates practice on fewer graphemes and can push a few of them over that specific bar. That's a real tradeoff, not a bug I'm hiding.

To check whether the result holds up outside one lucky parameter setting, I ran a robustness sweep: forgetting rate at four values, item discrimination at three values, twelve combinations total. The accuracy gap stayed positive in all twelve, ranging from +0.098 down to +0.002 at the harshest corner (heavy forgetting, high discrimination). The baseline configuration reproduces the headline +0.0605 exactly. So the direction of the effect is robust. The margin is not, at the extreme end it's close enough to zero that I wouldn't stake much on it.

One more piece of evidence lives outside the adaptive-versus-static comparison: the grapheme-decomposition engine that everything above depends on has been checked against a hand-verified truth set and tiling rules over the full system dictionary, about 210,000 words. It correctly tiles and reconstructs 209,743 of them. The two known gaps are pinned by tests rather than hidden: a trailing-"e" drop affecting about half a percent of words, which is a real bug I've tracked rather than fixed, and an overlap in how split vowel spans get represented, which is a modeling choice rather than an error. The full offline test suite passes.

Every chart and CSV behind these numbers is git-tracked and regenerates exactly with a single command, along with a six-page sample illustrated book generated by the pipeline.

## What's built, what isn't, and what's next

Built and verified: the closed loop runs live in the web app, the de-circularized evidence above is real and reproducible, the illustrated book pipeline is folded into that live loop rather than sitting off to the side, and the full offline test suite is green.

Not live: I have a working Cloud Run deployment path but haven't deployed it publicly. And a confidence-repair feature I'd designed for the voice interaction (never penalizing a low-confidence attempt the same way as a clear miscue) is currently a no-op on the Gemini Live path, because that path doesn't expose per-word confidence today. I'm naming that as a known limitation rather than letting it pass as a shipped feature.

What's next, after this competition, is a self-improving content flywheel: every real session becomes an eval datapoint, with the same decodability checker acting as an always-on judge over live usage instead of only simulated learners. That's deliberately scoped as future work, not something I rushed to bolt on before a deadline.
